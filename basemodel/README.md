> 경마 예측을 분류가 아니라 **랭킹** 문제로 풀고, 유저가 6축 비율을 실시간으로 바꿔도

## 0. 이 폴더는 무엇이고, `pipeline/` 과 어떻게 다른가

| | `pipeline/` (정원) | `basemodel/` (건모) |
|---|---|---|
| 묻는 것 | **어떤 구조가 실제로 기여하는가** (S1→S2→S3→S4 단계별 측정) | **그 구조를 제품 계약에 어떻게 얹는가** (6축 슬라이더 · 프리셋 5종) |
| 산출물 | 실험 장부 + 채택 모델 S3 | 서비스에 나갈 축 점수 테이블 · 프리셋 · 허깅페이스 폴더 |
| 데이터 | `pipeline/data` (sync_dataset.sh) | **같은 것을 그대로 쓴다** |
| 채점 | 팀 채점기 `common.py` | **같은 것을 그대로 쓴다** |

**정원님 코드는 한 줄도 고치지 않았다.** 손실·이력 GRU·경주 패딩·평가 하네스는 개념을
가져와 이 폴더 안에 다시 구현했고, 출처를 파일마다 적었다.

### 0-1. 같은 진단, 다른 처방

정원님 §6-3 의 제안:

```
점수 = 베이스(S3) + λ · (w₁s₁ + … + w₆s₆)          # 슬라이더가 베이스를 '조절'
```

이 폴더가 택한 형태:

```
점수 = m · s_시장 + (w₁s₁ + … + w₆s₆)               # 시장을 축에서 빼내 프리셋 상수로
```

**진단은 같다** — 균등가중이 무너지는 원인은 축 품질이 아니라 결합식이다.
**처방이 다른 이유**는 무엇이 희석되는지를 다르게 봤기 때문이다.

정원님 타워의 6축은 스키마 그룹 F1~F6 이고 **F6(인기도)가 그중 하나**다. 균등가중이면
시장 신호가 1/6 로 희석된다. F6 단독이 38~39% 인데 나머지 다섯이 20~30% 이므로,
희석 자체가 −3.4%p 의 큰 몫이다.

이 폴더는 화면 계약(`schema.sql` §2)의 6그룹을 쓰는데 **거기엔 인기도가 없다.**
그래서 시장을 7번째 타워로 빼고 유저에게 노출하지 않은 채 **프리셋마다 고정 계수 m** 으로
얹었다. 배당형은 m 을 크게, 역배형은 음수로, 나머지 셋은 0 으로. 희석 비율을 전 프리셋에
강제하지 않고 **프리셋마다 고르게** 한 것이 차이다.

두 처방은 배타적이지 않다 — 베이스 항과 시장 항을 같이 둘 수도 있다. 어느 쪽이든
**기획·도연님과 확정이 필요하다**(정원님 §6-4 의 범위 확인 건과 같은 사안).

```
                                            │  artifacts/runs/*.pt
                     ┌──────────── 배포 (주 1회 배치) ─────────────────────┐
  game.parquet  ────▶│  export.py   게임풀 3,700경주 축 점수 사전 계산      │
                     │              프리셋 5종 가중치 적합 · 온도 T         │
                     └──────────────────────┬───────────────────────────┘
                        axis_scores.parquet │  meta.json
                                            ▼
                     ┌──────────── 운영 (유저 요청) ───────────────────────┐
                     │  BE: DB 조회   FE: Σ(가중치 × 축점수) → softmax     │
                     │  ★ 모델이 돌지 않는다                              │
                     └───────────────────────────────────────────────────┘
```

**핵심 계약** — 화면이 하는 계산은 이것뿐이다 (기능명세서 AI-06).

```
raw = (Σ_k  groupWeights[k] × ax_k) / 100  +  market × ax_market
p   = softmax(raw × T)      경주 안에서
```

`groupWeights` 는 유저 슬라이더 6개(합 100), `market` 은 **프리셋마다 고정된 상수**,
`T` 는 `meta.json` 의 온도. 유저가 슬라이더를 움직이면 곱셈 6번과 덧셈이 전부다.

## 2. 축 여섯 개 — 왜 이렇게 갈랐나

슬라이더 축 이름은 화면 계약(`docs/명세서/schema.sql` §2 `feature_group.code`)을 따른다.
데이터 스키마의 그룹(F1~F6)과 **같은 것이 아니다.** `config.py` 가 그 번역표다.

| 축 | 이름 | 스키마에서 가져온 것 | 칸 |
|---|---|---|---:|
| `CONDITION` | 컨디션 | F1 최근 폼·휴양·조교 | 15 |
| `SPEED` | 스피드 | F1 스피드지수 + 주파기록 육종가 | 5 |
| `RUNNING` | 주행 | F5 각질·초반위치·상3F | 12 |
| `JOCKEY` | 기수 | F3 기수·조교사·궁합 (+ 기수/조교사 임베딩) | 11 |
| `ENVIRONMENT` | 환경 | F4 거리·주로·날씨 + 거리적성 육종가 | 16 |
| `ABILITY` | 실력 | 마사회 레이팅 + F2 혈통 육종가 (+ 부마 임베딩) | 22 |
| `MARKET` | (시장) | F6 배당 — **슬라이더 아님** | 3 |
| `CORE` | (공유) | 공통 X + 경주 내 상수 | 43 |

**경주 내 상수는 슬라이더에 올리지 않았다.** 거리·등급·두수·함수율·날씨·선행마수·혼전도
7개는 경주 안 모든 말이 같은 값이라 가중치를 올려도 순위가 안 바뀐다(valid 1,254경주에서
100% 상수 실측). 대신 `CORE` 로 보내 **모든 타워가 공유**한다 — 타워 안에서 말별 피처와
곱해질 때는 "이 말이 불량주로에서" 같은 의미가 생긴다.

### 시장(배당) 축을 슬라이더에서 뺀 이유

기획의 6그룹에 인기도가 없다. 그런데 베이스 모델 5종 중 둘(배당형·역배형)은 배당이
정체성이다. 그래서 시장을 **7번째 타워로 두되 유저에게 노출하지 않고, 프리셋마다
고정 계수 `m`** 으로 얹는다.

- `m > 0` → 시장을 따라간다 (**배당형**)
- `m < 0` → 시장이 저평가한 말을 고른다 (**역배형**)
- `m = 0` → 배당을 안 본다 (기본형·사람형·상승세형, 그리고 **주말 실시간 전부**)

슬라이더 6개 합이 100 이라는 화면 계약은 그대로다. `m` 은 `meta.json` 에서 온다.
배당은 tier=G(확정배당 = 경주 후 값)라 **과거 경주 리플레이 전용**이고, 주말 실시간
모델(73피처)에서는 타워 자체가 만들어지지 않는다.

## 3. 모델 구조

```
                      ┌─ CORE 43칸 ─┐
                      │             ▼
입력 [경주, 최대16두, 125칸] ──▶ trunk MLP ──┐   (경주 상황 — 전 축 공유)
                                             │
기수·조교사·부마 ID ──▶ Embedding(16) ────────┼──▶ 소속 타워에만
                                             │
말별 직전 20출전 ──▶ GRU(64) ────────────────┼──▶ 축마다 다른 선형 읽기
                                             │
                                             ▼
        축 k 피처 + trunk + 이력읽기(+임베딩) ──▶ 타워 MLP ──▶ 경주 내 z-score  s_k
                                                                        │
                        m·s_MARKET + Σ w_k·s_k  ──▶ 경주 내 softmax ──▶ 1착 확률
```

| 부품 | 역할 | 소속 |
|---|---|---|
| `nn.Linear` × 2 | 경주 상황 공유 표현 | 전 축 |
| `nn.Embedding` × 3 | 기수·조교사·부마 ID → 16차원 | 기수 / 실력 축 |
| `nn.GRU` × 1 | 말별 직전 20출전을 **순서대로** 읽음 | 축마다 다른 선형 읽기 |
| MLP × 7 | 축 점수 → 경주 내 z-score | 축 하나씩 |

- 사전학습 가중치 없다. 구조를 직접 정하고 이 데이터로만 0 에서 학습했다.
- 손실은 **Plackett–Luce** listwise, 1~3착까지 전개. 조건부 로지스틱 회귀(Benter 1994)
  = ListNet 과 같은 뼈대다. `softmax` 가 **경주 안에서만** 걸리는 게 전부이고,
  그것 하나 때문에 확률 합이 100% 로 자동으로 맞고 말끼리 경쟁 관계가 생긴다.

### 부품마다 소속을 정한 이유

전적 GRU 를 공유 표현에 통째로 넣으면 모든 타워가 같은 것을 보게 되어 축 간 상관이
올라가고 **슬라이더가 죽는다.** 그래서 기수 임베딩은 기수 축에, 부마 임베딩은 실력 축에
주고, 이력은 축마다 다른 선형으로 읽게 했다.

### 학습 중 가중치를 랜덤으로 뽑는다

그냥 만들면 학습 때 본 적 없는 가중치 조합에서 무너진다.

```python
매 배치:  w ~ Dirichlet(α=0.7)            # 가끔 한 축에 몰린 조합이 나온다
          m ~ Uniform(0, 2.0)              # 시장 계수
          손실 = PL( Σ w_k·s_k )                     # ① 시장 없이 (프리셋 3종·주말 실시간)
               + PL( m·s_MARKET + Σ w_k·s_k )        # ② 시장 포함 (배당형·역배형)
               + λ · 축간상관벌점
          역전파
```

효과 셋 — ① 각 타워가 혼자서도 쓸모 있어야 한다 ② 어떤 조합이 와도 안 무너진다
③ 드롭아웃 같은 정규화. **"유저가 모델을 실시간으로 바꾸는데 왜 재학습이 필요 없나요?"
에 대한 정확한 답**이기도 하다.

**손실이 둘인 이유 — 실측으로 얻은 교훈.** 처음엔 ②만 썼다. 그랬더니 시장 타워가 손실을
혼자 줄여버리고 여섯 축이 무임승차했다 — 축 단독 top-1 이 30%대에서 8~25% 로 무너지고
실력 축은 **무작위(10.2%)보다 낮은 8.0%** 가 됐다. 시장이 너무 좋은 지름길이었다.
서빙에서 실제로 쓰는 두 조건을 둘 다 손실에 넣자 회복됐다(균등 가중 32.5% → 33.7%).

**m 을 음수로 샘플링하지 않는 것도 실측이다.** 처음엔 `U(−0.6, +0.6)` 으로 뒀는데 시장
타워가 망가졌다(top-1 5.7% — 무작위보다 낮고, 시장확률과 상관 0.31). m 이 반은 양수
반은 음수라 "1착마 점수를 올려라"와 "내려라"가 상쇄되어 배울 방향이 없었던 것이다.
**시장 타워는 인기도를 일관되게 학습하고, 부호를 뒤집는 것은 프리셋(m<0)의 몫이다.**

### 축 간 상관 벌점

축이 전부 같은 말을 가리키면 유저가 비율을 바꿔도 순위가 안 바뀐다. 축 점수가 이미
경주 내 z-score 라 상관계수가 곱의 평균과 같다는 점을 이용해 손실에 벌점을 더한다
(`losses.axis_decorrelation`). 계수 λ 는 실측으로 골랐다 — §5.

## 4. 베이스 모델 5종 — 손으로 고른 숫자가 아니다

기능명세서 MP-01 은 "각 모델은 시작 가중치 분배만 다름"이라고만 정한다. 그 숫자를
손으로 정하면 근거를 댈 수 없으므로, 프리셋마다 **목적함수를 정하고 학습 구간에서
최적 가중치를 찾는다** (`presets.py`).

| 키 | 이름 | 제약 | 목적함수 | 시장 계수 m |
|---|---|---|---|---|
| `BASIC` | 기본형 | 없음 | 1착 적중 최대 | **0 고정** |
| `HUMAN` | 사람형 | 기수 40 고정 | 1착 적중 최대 | **0 고정** |
| `MOMENTUM` | 상승세형 | 컨디션 40 고정 | 1착 적중 최대 | **0 고정** |
| `ODDS` | 배당형 | 없음 | 1착 적중 최대 | 적합 (+0.6~2.0) |
| `UPSET` | 역배형 | **기본형 가중치 상속** | **고배당 적중 최대** | 적합 (−0.8~0) |

**앞의 셋은 배당을 보지 않는다(m=0).** 처음엔 셋 다 m 을 자유롭게 맞추게 했더니
전부 상한(0.79)에 붙었다 — 시장이 워낙 강한 신호라 목적함수가 top-1 이면 언제나 그렇게
된다. 그러면 다섯 모델이 전부 '시장 추종'이 되어 나눈 의미가 사라진다. 배당은 배당형의
정체성이고 역배형은 그 반대다. 나머지 셋은 실력으로 승부한다.
**부수 효과 — 앞의 셋은 배당을 전혀 안 보므로 프리셋 정의가 주말 실시간에 그대로 넘어간다.**
단 **체크포인트는 다르다.** 77피처 모델은 배당 파생 피처가 입력에 있어 배당 없는 환경에서
돌지 않는다. 주말 실시간은 73피처 체크포인트를 쓰고, 프리셋 가중치만 같은 절차로 다시 맞춘다.

> 여기서 실수를 하나 했다. 혼전도(`F6_field_entropy`)는 경주 내 상수라 처음엔 공유 칸(CORE)에
> 뒀는데, **그건 배당에서 나온 값**(tier=G)이라 모든 타워가 시장 정보를 보게 된다. 그러면
> "m=0 이니 배당을 안 본다"가 거짓말이 되고 주말 실시간으로 옮길 때 조용히 망가진다.
> 지금은 MARKET 축에 있다 — 경주 내 상수라 혼자서는 순위를 못 바꾸지만, 타워 안에서
> 인기도와 곱해지면 "혼전 경주에서는 인기마를 덜 믿는다" 같은 상호작용이 된다.

**역배형은 기본형의 가중치를 그대로 물려받고 시장 계수만 음수로 맞춘다.**
여섯 축까지 같이 맞추게 뒀더니 목적함수가 **가장 약한 축**(실력, 단독 top-1 21.5%)에
94 를 몰아줬다. 고배당마를 고르긴 하는데 실력이 있어서가 아니라 그 축이 부정확해서다
(교차적합에서 평균배당 34.8 → 14.1 로 흔들린 것이 증거). 역배의 올바른 정의는
**"펀더멘털은 좋다는데 시장은 아니라는 말"** 이고, 그건 기본형 점수에서 시장 점수를
빼는 것이다. Benter(1994) 의 2단계(펀더멘털 → 시장 결합)를 뒤집은 형태다.
맞출 숫자가 하나뿐이라 과적합할 여지도 없다.

- **고배당 적중** = 단승배당 **10~50배** 인 말을 골라 그 말이 1착. `schema.sql` 의
  `is_upset_hit`(리더보드 UPSET 축)과 같은 방향이다.
  상한을 두는 이유 — 없으면 목적함수가 90배짜리 말만 고른다(실측 평균배당 91).
  그런 말은 1% 미만으로 이겨서 유저가 영원히 못 맞힌다.
- 목적함수 둘 다 미분 불가능해서(argmax · 배당 임계값) 심플렉스 위 랜덤 탐색으로 푼다.
  다섯 프리셋에 **같은 절차**를 써야 비교가 성립한다.
- **최댓값 한 점이 아니라 상위 1% 후보의 평균**을 쓴다. 심플렉스 위에서 목적함수가
  평평해(꽤 다른 가중치가 오차 안에서 같은 점수) argmax 를 집으면 표본 잡음을 프리셋으로
  굳히게 된다. 평균은 재현 가능하고 해석도 자연스럽다.
- **적합은 train, 보고는 valid.** valid 로 고르고 valid 로 채점하면 모의고사로 고르고
  모의고사로 점수를 내는 것이라 부풀려진다. `crossfit_report()` 가 valid 2-fold 로 재확인한다.
- 배당형·역배형은 확정배당 기반이라 **주말 실시간 예측에서 빠진다**(73피처 모드에서
  자동으로 제외된다). 기능명세서 MP-01 의 "배당형·역배형은 주말 실시간 예측 제외"와 일치한다.

### 확률 계약 — 경주 내 정규화가 필요한 이유

축 점수는 각각 경주 내 z-score 지만 가중합의 폭은 가중치가 몰릴수록 넓어진다. 온도 T 를
균등 가중에서 맞추고 극단 가중치에 그대로 쓰면 확률이 무너진다.

| 계약 | 극단 가중치 최악 오차 (예측 − 실제, 상위 5%) | |
|---|---:|---:|
| | 77피처 | 73피처 |
| `softmax(raw × T)` | 26.9%p | 29.7%p |
| **`softmax(znorm(raw) × T)`** | **9.0%p** | **7.8%p** |

경주 내 정규화 한 줄로 극단 가중치에서의 오차가 26.9%p → 9.0%p 로 줄었다. `meta.json` 의
`normalize_within_race: true` 가 이 계약을 지시한다.

| 혼전도(엔트로피) | 경주 | 인기마 패배 | 고배당 우승 | 1착 평균배당 |
|---|---:|---:|---:|---:|
| 낮음 (독주) | 314 | 44.3% | 15.9% | 6.7 |
| ↓ | 313 | 61.0% | 19.5% | 7.6 |

혼전 경주에서 인기마가 71% 진다. 같은 구간에서 프리셋별 성적:

| 혼전도 | 기본형 적중 / 평균배당 | 역배형 적중 / 평균배당 | 배당형 적중 / 평균배당 |
|---|---|---|---|
| 낮음 | 48.4% / 3.0 | 40.8% / 11.8 | 53.5% / 1.8 |
| 높음 | 23.9% / 4.8 | 15.3% / 21.0 | 24.5% / 3.9 |

**혼전 경주일수록 세 프리셋의 격차가 좁아지고 역배형의 배당만 커진다** — 시장이 헷갈릴 때
역배형이 가장 쓸모 있다는 뜻이다. 시장 계수 m 곡선도 같은 말을 한다(train 36,586경주):

```
m       −0.80  −0.70  −0.60  −0.50  −0.40  −0.30  −0.20  −0.10   0.00
고배당    0.69   0.79   0.90   0.93   0.94   0.87   0.78   0.68   0.61   (%)
적중                            └──── 봉우리 ────┘
```

시장을 빼기 시작하면 고배당 적중이 0.61% → 0.94% 로 **1.5배** 오르고, 너무 많이 빼면
다시 내려간다. 채택값 m = −0.49 는 그 봉우리다.

| | 무엇 | 시간 | 유저가 기다리나 |
|---|---|---:|---|
| 1 | 게임풀 전체 사전 계산 | **0.68s** | ✕ 배포 때 1회 |
| 2 | 실시간 추론 1경주 | 7.7ms | ✕ 주말 배치 |
| 2 | 실시간 추론 36경주 (주말 최대) | 278ms | ✕ |
| 3 | **슬라이더 재계산 10명 동시** | **0.06ms** | ○ |

**유저가 기다리는 경로는 3번뿐이고 10명 동시에 0.06ms — 15초 기준의 25만분의 1.**
사전 계산을 안 해도 게임풀 전체가 0.68초라 어느 쪽이든 여유가 크다.

## 7. 시장 대비 유의성 검정

```bash
uv run python -m basemodel.significance --ckpt artifacts/runs/axis_77_s20260901_final.pt
```

전체 로그는 `artifacts/logs/significance.log` (gitignore — 위 명령으로 다시 만든다).
팀 레포 공유본은 `docs/model/basemodel_geonmo.md` (S15P21A304).

### 방법

| 무엇 | 방법 | 왜 이렇게 |
|---|---|---|
| 적중률 차이 | **McNemar 정확검정** + 경주 단위 paired bootstrap | 같은 경주를 둘 다 예측하므로 짝지은 자료다. 독립표본 검정은 틀린다 |
| 정보 증분 | **조건부 로짓 우도비**(χ²₁) | `eta = a·log(시장확률) + b·모델점수` 에서 `b ≠ 0` 인가 |
| 결합 효과 | valid **2-fold 교차적합** | train 은 모델이 학습한 구간이라 in-sample 이다 (LGB train 45.97% vs valid 33.49%) |
| 동률 | **1/k 기대값** | 인기 1위가 2두면 실제 베팅은 한 두만 고른다. valid 16경주(1.3%) 해당 |
| 시장 점수 | **log(내재확률)** | 확률을 점수로 그냥 넣으면 softmax 가 한 번 더 걸려 거의 균등이 된다 |
| 음성 대조군 | **무작위 점수** | 검정이 제대로 도는지 확인. 통과(p=0.86) |

### 결과 한 줄씩

| 질문 | 답 | 숫자 |
|---|---|---|
| 시장을 이기나 | **아니오** | 기본형 −6.14%p [−8.69, −3.63] p<0.001 |
| 시장과 대등한가 | 배당을 쓰면 **대등** | 배당형 −1.59%p [−3.63, +0.36] p=0.29 |
| 시장이 모르는 정보가 있나 | **예, 확실히** | LR 19.11, p=1.2e−05 (무작위는 p=0.86) |
| 그 정보로 더 맞히나 | **아니오** | 결합 top-1 −0.16%p [−1.08, +0.76] |
| 확률은 좋아지나 | **예, 유의하게** | logloss 1.7504 → 1.7424, CI [−0.0147, −0.0012] |
| 한 시기의 우연인가 | **아니오** | 세 시기 −0.9 / −0.4 / +1.2 |
| 학습 운인가 | **아니오** | 시드 5개 33.43% ± 0.50 |

### 이 표본으로 무엇을 잴 수 있나

| | 값 |
|---|---|
| 최소 검출 가능 차이 (80% 검정력, α=.05) | top-1 **±2.39%p** · top-3 **±2.31%p** |
| 1%p 차이를 잡으려면 | 경주 7,172개 — 주말 40경주 기준 **148주** 더 |
| 2%p 차이를 잡으려면 | 경주 1,793개 — **13주** 더 |

**"차이 없음"은 "같다"가 아니라 "이 표본으로는 못 잰다"는 뜻이다.**

### 정리 — 유의성과 효과 크기는 다른 이야기다

모델은 시장에 없는 정보를 **확실히** 갖고 있고(p=1.2e−05), 시장 확률에 더하면 확률 품질이
**유의하게** 좋아진다. 그런데 그 크기가 1착마 확률의 상대 0.9% 라, **어느 말을 고르는지는
바뀌지 않는다.** 둘 다 사실이고 둘 다 적어야 한다.

**이 프로젝트의 값은 "시장보다 잘 맞힌다"가 아니다.** 유저가 자기 관점으로 모델을 바꿔가며
과거 경주를 맞히는 경험이고, 그러려면 시장을 이길 필요가 없다. 대신 확인해야 할 것은
슬라이더가 실제로 예측을 바꾸는가(축 상관 0.39)와 어떤 조합에서도 안 무너지는가
(축 단독 21.0~28.4%)이고, 둘 다 통과했다.

> **화면 문구 주의** — "AI가 시장보다 잘 맞힙니다"는 쓸 수 없다. 쓸 수 있는 것은
> "인기도를 넣으면 시장과 대등하고(통계적 차이 없음), 시장에 없는 정보를 갖고 있다"까지다.

## 11. 규칙 (깨면 비교가 무효)

- **정렬 유지** — `race_id` 연속 블록. 셔플은 경주끼리만.
- **game 3,700경주는 학습·검증·튜닝 금지.** 유저가 플레이할 경주다. 점수를 미리 매기는
  것(`serve.load_game`)만 허용된다.
- **test 는 최종 1회.** 비교와 튜닝은 valid 로 한다.
- **전처리는 train 에서만 fit** — 중앙값·평균·표준편차·원핫 어휘·범주형 사전·이력 표준화.
- **이력에는 그 경주보다 엄격히 이전 출전만.** `history.build` 의 assert 가 강제한다.
- 데이터를 직접 읽지 않는다. 전부 `team.C` 를 거친다.
