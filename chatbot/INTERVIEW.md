# RAG 챗봇 — 설명 + 예상 질문

> 면접·발표에서 이 챗봇을 설명하기 위한 문서.
> **모르는 건 모른다고 답하는 게 낫다.** 안 한 것은 아래 §6 에 정직하게 적어 두었다.

---

## 1. 30초 설명

> 경마 입문자용 사전 챗봇입니다. LLM 에 그냥 물으면 그럴듯하게 지어내기 때문에,
> 마사회 경마용어 사전 1,528개를 미리 색인해 두고 **질문에 맞는 항목을 먼저 찾아
> 근거로 함께 넘긴 뒤 "이 근거 안에서만 답하라"고 시킵니다.**
> 근거를 못 찾으면 답하지 않고 모른다고 합니다.
> 검색은 임베딩 대신 BM25 를 썼는데, 사전 질문은 용어가 질문에 그대로 들어 있어
> 키워드 검색이 더 정확하기 때문입니다.

## 2. 데이터 흐름

```
질문 "복승식이 뭐예요?"
  │
  ├─ ① 토큰화       → ['복승식이','복승식','복승','승식','뭐예요','뭐예']
  │                    조사 제거 + 2·3글자 n-gram
  ├─ ② BM25 점수    → 복승식 43.1 / 축마 19.7 / 이중복승식 19.1
  ├─ ③ 상위 3건     → 이게 "근거"
  ├─ ④ 임계값 검사  → 12점 미만이면 여기서 중단, "자료에 없음"
  ├─ ⑤ 프롬프트 조립 → [근거] + [질문] + 규칙 6개
  └─ ⑥ LLM 호출     → 실패하면 ③의 원문을 그대로 반환
```

| 단계 | 파일 |
|---|---|
| 수집 | `ingest_glossary.py` |
| ①②③ | `retriever.py` |
| ④⑤⑥ | `rag.py` |
| API | `server.py` |

## 3. 색인을 어떻게 만들었나

**자료구조 3개**를 만든다. 전부 메모리에 올린다 (1,528개라 가볍다).

### ① 역색인 `post` — 단어 → 그 단어가 든 문서 번호

```python
self.post: dict[str, list[int]] = defaultdict(list)
for i, t in enumerate(self.tf):
    for w in t:
        self.post[w].append(i)
```

```
"복승식" → [173, 318, 634, 663, 916, 1077, ...]
```

질문에 든 단어만 보면 되므로 1,528개를 전부 훑지 않는다. **이게 검색이 빠른 이유다.**

### ② 단어 빈도 `tf` + 문서 길이 `len`

```python
t = Counter(tokens(d.text))   # 이 문서에서 각 단어가 몇 번 나오나
self.tf.append(t)
self.len.append(sum(t.values()))
```

### ③ IDF — 흔한 단어의 가치를 낮춘다

```python
self.idf = {w: math.log(1 + (n - c + 0.5) / (c + 0.5)) for w, c in df.items()}
```

`n` 은 전체 문서 수, `c` 는 그 단어가 등장한 문서 수.

| 단어 | 등장 문서 | IDF |
|---|---:|---:|
| 복승식 | 8개 | 5.19 |
| 말 | 173개 | 2.18 |
| 경주 | 567개 | 0.99 |

"경주"는 어디에나 있어 변별력이 없다 → 점수를 거의 안 준다.
"복승식"은 8개에만 있어 강한 신호다 → 점수를 크게 준다.

### ④ 용어명 정확매칭 표 `by_term`

```python
for name in {d.term_ko, re.sub(r"\(.*?\)", "", d.term_ko).strip()}:
    self.by_term[name.lower()].append(d.idx)
```

`"동요병(動搖病)"` 은 `"동요병"` 으로도 색인한다. 질문에 용어명이 통째로 들어 있으면
글자 수 × 6점을 가산한다 — 사전 질문의 특성을 이용한 장치다.

**규모**: 문서 1,528개 · 단어 35,317종 · 문서당 평균 255조각. 색인 생성 1초 미만.

## 4. BM25 — 무엇이고 왜 쓰나

검색에서 오래 쓰인 표준 점수 함수다. 1994년에 나왔고 지금도 강력한 기준선이다.

```python
scores[i] += idf * f * (K1 + 1) / (f + K1 * (1 - B + B * dl / avg))
```

| 기호 | 뜻 |
|---|---|
| `idf` | 그 단어가 얼마나 희귀한가 |
| `f` | 이 문서에서 그 단어가 몇 번 나오나 |
| `dl / avg` | 이 문서가 평균보다 긴가 |
| `K1 = 1.4` | 빈도의 포화 정도 |
| `B = 0.75` | 문서 길이 보정 강도 |

**TF-IDF 와의 차이 두 가지** — 면접에서 자주 묻는다.

1. **빈도가 포화한다.** TF-IDF 는 단어가 10번 나오면 1번의 10배 점수다. BM25 는
   `f/(f+K1)` 꼴이라 어느 지점부터 더 안 오른다. 같은 말을 반복한 문서가 이기는 걸 막는다.
2. **문서 길이를 보정한다.** 긴 문서는 우연히 단어를 포함할 확률이 높다. `B` 로 그만큼 깎는다.

`K1=1.4`, `B=0.75` 는 **문헌의 관행값을 그대로 썼다.** 튜닝하지 않았다(§6 참조).

## 5. 할루시네이션을 어떻게 막았나

세 겹으로 막는다.

| 겹 | 방법 |
|---|---|
| 1 | **근거 없으면 LLM 을 아예 부르지 않는다.** 점수 12점 미만이면 "자료에 없음"으로 즉시 반환 |
| 2 | **프롬프트에서 근거 밖 내용을 금지한다.** "아래 근거에 있는 내용만 사용한다. 없으면 지어내지 않는다" |
| 3 | **출처를 항상 함께 반환한다.** 사용자가 원문을 확인할 수 있다 |

```python
if not hits or hits[0][1] < MIN_SCORE:
    return Answer("제가 가진 자료에는 없는 내용이에요…", [], False, "근거 없음")
```

실제로 "오늘 저녁 뭐 먹지?"를 물으면 `sources: []` 와 함께 모른다고 답한다.

## 6. 안 한 것 — 물어보면 이렇게 답한다

정직하게 인정하는 편이 낫다. 대안까지 말할 수 있으면 더 좋다.

| 안 한 것 | 어떻게 답하나 |
|---|---|
| **임계값 12점을 튜닝 안 했다** | 몇 개 질문을 돌려보고 경험적으로 잡았습니다. 제대로 하려면 질문 30~50개에 정답 라벨을 붙여 정밀도·재현율 곡선을 그리고 정해야 합니다 |
| **BM25 파라미터를 튜닝 안 했다** | 관행값(k1=1.4, b=0.75)입니다. 평가셋이 없어 튜닝의 근거를 만들 수 없었습니다 |
| **검색 정확도를 정량 평가 안 했다** | 가장 큰 공백입니다. 질문 30개에 정답 용어를 붙여 Recall@3 을 재는 게 다음 작업입니다 |
| **임베딩을 안 붙였다** | 사전 질문에는 BM25 가 유리하다고 판단했습니다. 다만 "돈 어떻게 걸어요?" 같은 우회 표현은 약합니다. `Retriever.search()` 인터페이스를 분리해 두어 하이브리드로 확장 가능합니다 |
| **청킹을 안 했다** | 사전 항목 하나가 평균 몇백 자라 통째로 한 덩어리로 씁니다. 시행규정처럼 긴 문서를 넣으면 청킹이 필요합니다 |
| **대화 맥락을 안 쓴다** | 세션은 저장하지만 답변에 반영하지 않습니다. "그럼 그건요?" 같은 지시어 질문은 못 풉니다 |
| **재순위(rerank)를 안 했다** | 상위 3건을 그대로 씁니다. 크로스 인코더로 재순위하면 정확도가 오르지만 모델이 필요합니다 |

## 7. 예상 꼬리질문

### Q. RAG 가 뭔가요?
검색으로 근거를 찾아 LLM 에 함께 넘기고, 그 근거 안에서만 답하게 하는 방식입니다.
LLM 이 지어내는 걸 막고, 출처를 제시할 수 있습니다. 모델을 다시 학습시키지 않고
자료만 갈아끼우면 되는 것도 장점입니다.

### Q. 왜 벡터 DB 를 안 썼나요?
문서가 1,528개라 메모리에 다 올라갑니다. 검색이 1ms 안에 끝나서 벡터 DB 의
근사 최근접 탐색이 필요 없습니다. 운영 요소를 하나 늘리는 비용이 이득보다 큽니다.
문서가 수십만 개로 늘면 그때 도입하는 게 맞습니다.

### Q. 임베딩이 더 좋지 않나요?
질문 유형에 따라 다릅니다. 사전 질문은 "복승식이 뭐예요?"처럼 **찾을 용어가 질문에
그대로 있어서** 키워드 검색이 정확합니다. 임베딩은 "돈 어떻게 걸어요?" 같은
우회 표현에 강합니다. 실제 사용 로그를 보고 후자가 많으면 하이브리드로 가야 합니다.

### Q. 한국어 형태소 분석은 어떻게 했나요?
안 했습니다. konlpy 는 자바 의존이라 배포가 무거워집니다. 대신 두 가지로 근사했습니다.
① 조사·어미 40여 개를 뒤에서 떼어냅니다 — "복승식이" → "복승식".
② 2·3글자 n-gram 을 함께 색인합니다 — 조사 목록에 없는 변형도 부분 일치로 걸립니다.
정확도는 형태소 분석기보다 낮지만 의존성이 없고, 이 도메인에서는 충분했습니다.

### Q. 왜 IDF 에 로그를 쓰나요?
빈도 차이를 압축하기 위해서입니다. 1개 문서에 나오는 단어와 1,000개에 나오는 단어의
가치 차이는 1,000배가 아니라 그보다 훨씬 작습니다. 로그가 그 감각에 맞습니다.

### Q. 문서가 100만 개가 되면요?
세 가지가 바뀝니다. ① 역색인을 메모리에 못 올리니 Elasticsearch 나 디스크 기반
인덱스로 옮깁니다. ② 임베딩 + 벡터 DB 로 후보를 좁히고 BM25 로 재순위하는
하이브리드가 유리해집니다. ③ 색인 갱신을 배치로 돌려야 합니다.

### Q. LLM 이 죽으면요?
검색된 사전 원문을 그대로 반환합니다. 답변 문장이 덜 다듬어질 뿐 챗봇은 살아 있습니다.
아웃바운드가 막힌 환경을 가정하고 설계했습니다.

### Q. 응답 시간은요?
검색은 1ms 미만입니다. 대부분 LLM 호출 시간(1~3초)입니다.
LLM 없이 쓰면 전체가 10ms 안에 끝납니다.

### Q. 평가는 어떻게 하실 건가요?
질문 30~50개에 정답 용어를 라벨링해 **Recall@3**(정답이 상위 3건에 있나)을 재고,
관련 없는 질문 10개로 **오답률**(근거 없음을 제대로 판정하나)을 봅니다.
그 뒤에 임계값과 BM25 파라미터를 조정합니다. 지금은 이 평가셋이 없는 게 약점입니다.

### Q. 프롬프트 인젝션은요?
사용자 질문이 프롬프트에 들어가므로 "이전 지시를 무시하라" 같은 공격이 가능합니다.
지금은 막고 있지 않습니다. 근거가 사전 원문으로 고정돼 있어 피해 범위는 제한적이지만,
질문 길이 제한(500자) 외에 방어가 없다는 건 인정해야 합니다.

### Q. 왜 사전을 직접 긁었나요?
스키마에 "마사회 경마 용어집"이 명시돼 있는데 파일이 없었습니다.
마사회 경마가이드 페이지가 로그인·API 키 없이 공개돼 있어 153페이지를 수집했습니다.
페이지 인코딩이 EUC-KR 이라 UTF-8 로 읽으면 깨지는 함정이 있었습니다.
