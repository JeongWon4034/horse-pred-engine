# 사이드 실험 장부 (브랜치 `exp/side`)

본 실험(`feat/dl-stages`, `experiments/ledger.md`)은 건드리지 않고 옆에서 돌린 것들. 기존 코드 수정 없음 — 새 파일만
(`model/score.py` `model/side_train.py` `model/side_roi.py` `model/side_ensemble.py` `side_sweep.sh`).
같은 자(팀 채점기), 같은 데이터(f17ca36), 같은 규칙(game 학습 금지·test 미개봉·경주 단위 셔플·hrNo 미사용).

## 1. game ROI — 학습된 모델로 game 3,700경주 점수 → 실배당 단승 1단위

`model.score --split game` 이 체크포인트(`experiments/runs/*.pt`)와 train 에서 다시 fit 한 전처리로 game 점수를 뽑는다.
이력은 train∪valid 풀에서 `rcDate < 경주일` 만 (game 행은 풀에 없음). LightGBM 은 같은 train 으로 재학습해 game 예측.

### 1-1. 결과 (전략 top1 = 매 경주 모델 1위마)

| 모델 | 베팅 | 적중 | ROI | 적중 평균배당 |
|---|---:|---:|---:|---:|
| 시장 (인기 1위마) | 3,687 | 37.3% | −20.7% | 2.12 |
| LightGBM 73 | 3,678 | 33.0% | −5.8% | 2.86 |
| LightGBM 77 (배당 포함) | 3,687 | 38.2% | −13.4% | 2.27 |
| S3 L10 단일 | 3,679 | 34.4% | −1.0% | 2.88 |
| S3 L10 seed5 평균 | 3,680 | 34.6% | −0.7% | 2.87 |
| S3 L20 seed5 평균 | 3,679 | 34.6% | **+0.5%** | 2.90 |
| LGB73 + S3 L20 (5:5) | 3,680 | 34.1% | −3.8% | 2.82 |

조건부 베팅(모델 확률 − 시장 확률 ≥ t 인 경주만): S3 L20 t=0.10 에서 1,136베팅 **+37.2%**, LGB t=0.10 +18.4%.
EV(확률×배당) 최대 말 베팅: S3 +19~26%, LGB −13%.

### 1-2. 이게 진짜인가 — 누수 점검

- **피처 누수 없음.** 첫 출전 말(F1_first_start=1)의 생애 성적이 game·valid·train 전부 NaN(현재 경주 결과 미포함). F1/F2/F3/F4 피처와 y_win 상관이 세 분할에서 동일(예: F1_win_rate_life +0.163/+0.166/+0.168).
- **적중률은 valid 와 같다.** LGB game 33.0% vs valid 34.0%, S3 34.6% vs 34.8%. 모델이 game 에서 더 잘 맞히는 게 아니다.
- **그런데 valid 에서 같은 전략을 재현하면 수익이 사라진다** (valid 에 배당 컬럼이 없어 `0.800/F6_mkt_prob` 로 역산 — game 에서 검증: 이 추정으로 시장 ROI −20.7% 정확히 재현):

| valid 1,254경주 | 적중 | ROI | 적중배당 |
|---|---:|---:|---:|
| 시장 | 39.3% | −16.6% | 2.12 |
| LightGBM 73 | 34.0% | −9.3% | 2.67 |
| S3 L20 seed5 평균 | 34.8% | −8.6% | 2.63 |
| LGB73 + S3 (5:5) | 35.3% | −7.7% | 2.61 |
| 조건부 t=0.03~0.10 (베팅 240~600) | 24~29% | −0.2 ~ +13.0% | 3.6~4.6 |

- **해석**: game 의 좋은 ROI 는 **시기 혼재** 때문이다. game 은 2015~24 개최일의 15% 를 뺀 것이고 train 은 그 사이사이 날짜를 전부 포함한다. 모델은 "그 시즌에 누가 잘 뛰었는지"를 이미 봤다(적중률은 같지만 배당 높은 말 쪽으로 정확히 기운다). valid(2025-11~2026-05, train 뒤)는 이 이점이 없다.
- **정직한 기대치는 valid 값이다**: 모델은 인기마보다 **8%p 덜 잃는다**. 매 경주 베팅으로 이익은 안 난다. 조건부 베팅은 손익분기 근처지만 베팅 수가 적어(±15%p) 확정 못 한다.
- **게임 서비스 관점**: 유저가 플레이하는 game 경주에서 AI 가 실제보다 강하게 보인다는 뜻. 온보딩 프리셋 ROI 표기는 game 값이 아니라 valid 값(또는 그 사이의 보수적 값)을 써야 한다. 이건 팀에 알릴 사항.

읽기:
- **축 간 상관 ≤ 0.9 목표는 여유 있게 통과**(최대 0.63). 슬라이더를 움직이면 예측이 실제로 달라진다.
- **축 단독 바닥 ≥ 25 는 77 에서 F3(24.3)·F4(23.1) 미달**, 73 에서는 전부 통과(25.0~29.7). 조건(F4) 축은 피처 7개뿐이라 단독으로 약한 게 자연스럽다. 무작위 10.2 보다는 훨씬 위.
- **77 균등 가중이 LGB 보다 유의하게 나쁘다(−2.3%p).** 랜덤 가중치로 학습하면 "어떤 가중치에서도 무너지지 않게" 되는 대신 특정 가중치에서의 최고점을 포기한다 — 스펙이 원하는 성질이지만 종합 정확도 비용이 2%p. F6 단독(38.4)이 시장(39.3) 근처인 건 인기도 축이 배당을 그대로 옮기기 때문.
- **73 균등 가중 34.9 는 LGB 와 동률**이고 S3(35.0) 과도 같다 — 인기도 없는 게임 모드가 필요하면 이 타워를 그대로 쓸 수 있다.
- 다음: 종합 헤드(가중치 고정 1)를 축 옆에 따로 두어 "균등 가중 정확도 손실" 을 없애는 변형, S3 이력 GRU 를 F1 축 입력으로 넣는 변형. game ROI 프리셋 3종은 §1 의 시기 혼재 문제 때문에 valid 역산 배당으로 재야 한다.

### 6-1. 부수 발견 — 기존 epoch 선택 규칙이 학습 덜 된 모델을 고른다

`side_tower.py` 는 `(top1, -logloss)` 순으로 best 를 고른다. 균등가중 top-1 이 초기 epoch 에 크게 튀어(가중치가 Dirichlet 랜덤이라 축 타워가 덜 학습된 상태에서도 균등가중이 우연히 높다) **ep1 이 선택된다.** 2회 재현.

| 축 단독 top-1 | ep1 (기존 규칙) | logloss 기준 |
|---|---:|---:|
| F1 전적 | 30.62 | 29.74 |
| **F2 혈통** | **17.94** | **25.28** |
| F3 기수 | 21.85 | 25.76 |
| **F4 조건** | **19.46** | **23.68** |
| F5 구간 | 28.95 | 29.98 |
| F6 인기도 | 39.00 | 37.48 |

**유저가 혈통 축을 끝까지 밀면 17.9% 예측을 받게 되어 있었다.** 슬라이더 제품에서 치명적이다. `--select logloss` 를 기본으로 두고 `--select top1` 로 기존 규칙을 재현할 수 있게 남겼다. 매 실행에서 두 규칙이 각각 어디를 고르는지 같이 출력한다.

S3(`train.py`)는 같은 규칙으로도 ep6~14 가 뽑히므로 **이 문제는 타워 전용**이다 — 원인이 Dirichlet 가중치 샘플링이라는 것과 일관된다. 기존 `side_tower.py` 는 사이드 실험 규칙(기존 코드 무수정)에 따라 손대지 않았다. **팀 백로그로 넘긴다.**

epoch 선택을 logloss 기준으로 통일하고 대조군(`--no-hist`)과 짝 비교했다.

### 6-3. 판정 — 축 개선으로는 해결되지 않는다. 결합식 문제다

`models.py:TowerRanker.forward` 가 이렇다.

```
점수 = w₁·s₁ + w₂·s₂ + … + w₆·s₆
```

**베이스 모델 점수가 식에 없다.** 유저가 슬라이더를 균등으로 두면 S3 가 나오는 것이 아니라 S3 와 무관한 타워 모델이 나온다. 즉 지금 구조는 베이스를 **조절**하는 것이 아니라 **대체**한다. 기획서 `docs/01` §154 의 결합식도 같은 형태라 코드가 기획을 정확히 따랐고, 문제는 기획 단계에 있다.

두 번 확인했다 — epoch 규칙을 고쳐도(6-1), 축에 GRU 를 넣어도(6-2) −3.4%p 는 그대로다.

**제안하는 형태** (이 레포 범위 밖 — 기획·도연님과 확정 필요):

```
점수 = 베이스(S3) + λ · (w₁s₁ + … + w₆s₆)
```

- 슬라이더 전부 0 → 정확히 S3
- `λ` 는 valid 로 "정확도 손실 vs 슬라이더 반응성"으로 결정
- 서버 부담 불변 — 베이스 점수도 캐시하면 곱셈 6번 + 덧셈 1번

### 6-4. 범위 확인 필요

`docs/08` §8-5 · §10-3 에 **도연님이 별도 6축 축 점수 파이프라인을 갖고 있다**는 기록이 있다. 서비스에 나갈 축 점수가 S5 에서 나오는지 도연님 쪽에서 나오는지 확정되지 않은 상태다. 이 실험 이상 파기 전에 소유 범위를 정해야 한다.
